Cross-schema read (core → `wallet.identity_links`) is a deliberate single-database-phase seam behind the `IdentityLinkReader` interface; a split-service topology swaps in a ledger-projection reader (fed by AccountLinked/AccountUnlinked) with no change to `resolve`/`IdentityStore`. This closes the gate item **"walletless-T1 via `sub_hash` proven."**

**Security self-review (T1 pricing is a trust decision):**
- *Inputs validated?* The resolver stays a pure function of fetched data; `resolve(undefined,…)` is still unconditionally T3. An agent-supplied `sub_hash`/`member_ref` only ever MATCHES an existing active link/seeded row — it cannot forge tier: presenting an unknown value resolves T3, and the value is used only as an equality key in a parameterised query, never as a tier assertion.
- *Signatures/trust verified before trust?* T1 requires an `active` link (or active seeded row) to actually exist; a revoked link is authoritative and never resolves T1, so a stale/withdrawn consent cannot buy member pricing. The raw subject never appears — `identity_ref` is the tokenised member_ref.
- *Secrets/keys never logged?* No token/secret material is read or logged; the reader selects only `member_ref, sub_hash, consumer_ref, status`. `sub_hash` is already a hash.
- *Replay/idempotency considered?* Reads are live and uncached, so there is no stale-cache replay window — revocation lands on the next resolution (asserted end-to-end at the quote level). Parameterised SQL throughout; the interpolated `column` is a compile-time union, never caller input.

## PH1-16 — B14 Consent & Mandate service · ✅ 2026-07-05

**Built:** the consent & mandate service (`apps/wallet/src/modules/mandates`, migration `0004_mandates`), three routes wired session-guarded. `grant` builds a `Mandate` from the consumer's `MandateGrantRequest`, signs the attestation via the platform `Signer` (FakeSigner in dev; the real Ed25519 signer via factory in prod — consumer-held keys are out of scope in Ph 1), persists it and emits `MandateGranted`. `attenuate` overlays a narrowing patch on the parent to build a CHILD (referencing `parent_id`) and REJECTS any escalation by construction via the pure `attenuationViolations` predicate — checked on every dimension: scopes/categories/merchants subset (parent `merchants:['*']` = all), per_txn/per_month/pre_authorised_up_to amounts, data_sharing (a child may not enable a flag the parent left off), and exp (a child may not outlive the parent). `revoke` flips status LIVE (`UPDATE … WHERE status='active' RETURNING`, idempotent) and emits `MandateRevoked`. `authoriseForQuote` is the wallet-path `checkout:execute` gate: it reads status LIVE (no cache), returns `MANDATE_REVOKED` for a revoked/expired mandate, `LIMIT_EXCEEDED` above `per_txn`, records an IMPLICIT `Approval {mode:'pre_authorised'}` (single-use per quote, `ApprovalGranted` emitted) for a quote at/below `pre_authorised_up_to`, and `APPROVAL_MISSING` above it when no explicit approval yet exists (explicit approvals are PH1-18, through the same table). Added `MandateGrantRequest`/`MandateAttenuateRequest` to `packages/contracts` (contracts-first).

**Tests:** 12 (workspace green). Gate property test (`attenuation.property.test.ts`, 4) — fast-check over scopes/limits/categories/merchants: whenever the predicate ACCEPTS a child, that child provably does not exceed the parent on ANY dimension (every concrete inequality asserted, 1000 runs); an equal child is a valid attenuation; widening EACH dimension is rejected on exactly that dimension; `merchants:['*']` permits any child list. Integration (`mandates.integration.test.ts`, 8) — grant → active, platform-attested, `MandateGranted` in the ledger; attenuate → narrower child with `parent_id`, widening `rejects`; pre-authorised quote ≤ threshold → implicit approval persisted + `ApprovalGranted`, idempotent (one approval row on replay); quote above threshold → `APPROVAL_MISSING`; quote above per_txn → `LIMIT_EXCEEDED`; **revocation mid-session → the next `authoriseForQuote` (the stub-agent checkout) returns `MANDATE_REVOKED`, status flipped live, `MandateRevoked` in the ledger, second revoke idempotent**; the hash chain verifies; the three routes 401 without a session. `pnpm -r build && pnpm -r test && pnpm lint` all exit 0.

**Deviation/notes:** none to plan scope. Categories are treated as a plain allow-list (more entries = more permissive; child ⊆ parent), avoiding an empty-means-all ambiguity; merchants keep the explicit `'*'` wildcard from the contract. The pre_authorised implicit approval is recorded here (§6.1 "nothing transacts without an approval object on the wallet path"); the explicit-approval issuance + re-mint is PH1-18, which reuses this `wallet.approvals` table and the same single-use-per-quote guarantee. The `authoriseForQuote` gate is exercised by a stub agent here; it is re-run against the real Valet checkout in Phase 2.

**Security self-review (consent path — mandate authority):**
- *Inputs validated?* Yes. `MandateGrantRequest`/`MandateAttenuateRequest` are Zod-parsed at the route; the built `Mandate` is `Mandate.parse`d (enforcing the limit ordering pre_auth ≤ per_txn ≤ per_month) before any write. Attenuation is validated child-⊆-parent on every dimension before persistence.
- *Escalation impossible by construction?* Yes — that is the headline invariant. `attenuate` computes `attenuationViolations(parent, child)` and throws `MandateWideningError` on any non-empty result, so a widened mandate can never be persisted or emitted; the property test proves the predicate over 1000+ generated cases. Attenuation also requires the parent to be the caller's own active mandate.
- *Signatures/trust verified before trust?* Every mandate and approval carries a platform `Signer` attestation over a canonical serialisation; the checkout gate trusts only a LIVE `active` mandate status (a revoked/expired mandate never authorises), so withdrawn consent cannot transact.
- *Replay/idempotency considered?* Revocation is a single atomic live `UPDATE … WHERE status='active'` (idempotent); approvals are single-use per quote (`UNIQUE(quote_id)`, a losing race re-reads the winner's row, one `ApprovalGranted` only); `MandateGranted`/`MandateRevoked`/`ApprovalGranted` all land in the hash-chained ledger and it re-verifies. Parameterised SQL throughout; no secret/key material is logged (attestations are signatures, not keys).
